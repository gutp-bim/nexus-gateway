# MQTT Connector subscriptions converge live from the Point List, not on restart

**Status:** accepted — 2026-08-22

EP-006/FEAT-026 (ADR-0003) closed with the Connector poll/subscribe-list reload deferred: connectors picked up Point List changes only on restart, "acceptable at MVP scale." Issue #119 closes that gap for the MQTT connector: `internal/mqttsync` (gateway-side, `cmd/gateway`) derives the desired MQTT subscription set from the same synced Point List snapshot the Normalizer resolver already holds, and an operator can preview it, then push it to a running `connector/mqtt.Connector` over a new NATS control subject (`cfg.mqtt.<connector_id>.{status,apply}`, mirroring the existing `cmd.mqtt.<connector_id>` write-command subject, §2.3/§2.4 of `docs/connector-spec.md`). The connector applies it live — `autopaho` `Subscribe`/`Unsubscribe` — with no restart and no telemetry gap for unaffected topics.

Other protocol connectors (BACnet, OPC-UA, WebSocket, ZeroMQ) are unaffected and remain restart-only; MQTT was the protocol issue #119 asked for, and the AGENTS.md rule that connectors stay isolated and receive only native addressing (never `point_id`) made it a natural first candidate — `sdk.SubscriptionSpec` carries topic/QoS/writability, nothing semantic.

## Decision

**Live hot-reload, not a container restart.** A restart-based apply (recreate the connector's Docker container with new `MQTT_POINTS`/`MQTT_SUBSCRIPTIONS` env vars, via `internal/lifecycle.Manager`'s existing Update/Rollback health-soak path) was the lower-risk alternative and was considered, since EP-006 had already deemed restart-based reload acceptable. It was rejected because it reintroduces a telemetry gap on every sync and does not need new subscribe/unsubscribe logic — but the issue's acceptance criteria ("retain the previous subscriptions on failure", atomic add/change/remove) are naturally satisfied by an in-process converge that never has to tear down the broker session at all. Chosen after confirming with the requester that the added complexity in `connector/mqtt` was acceptable.

**Atomic apply order: Subscribe first, Unsubscribe second, commit last.** `Connector.ApplySubscriptions` (connector/mqtt/connector.go) Subscribes every added/changed topic in one batch; if the broker rejects any of them, the call aborts *before* touching `c.topics` or issuing any Unsubscribe — so a failed apply leaves the previously applied subscriptions completely untouched, satisfying "retain the previous subscriptions on failure" without needing separate rollback bookkeeping. Only once every addition/change succeeds are the removed topics Unsubscribed (best-effort — a failure there is recorded in the reply's `errors` but does not block the commit, because the new `c.topics` no longer routes that topic anyway; a broker-side leftover subscription is inert, not a correctness problem).

**Command topic = subscribe topic, guarded with MQTT5 No Local.** Building OS's Point List (`GatewayPointEntry`/`GatewayPointDto` in `gutp-building-os-ri`) carries no MQTT-specific QoS or write-topic field — `NativeAddressingDto.From` is hardcoded to BACnet-only addressing and returns `null` for every other protocol. Confirmed with the requester: for a writable synced point, `command_topic` is the same string as the subscribe `topic` (no separate naming convention). Publishing a write to the same topic the connector is subscribed to would otherwise echo the write back to the connector as a spurious telemetry reading — an application-level loop, and if anything downstream reacted to that reading by issuing another write, a real one. `paho.golang` (MQTT5) exposes `SubscribeOptions.NoLocal`, which tells the broker never to deliver a client's own publishes back to that same client's subscription; `connector/mqtt` sets it whenever `Writable && CommandTopic == Topic`. This only suppresses the connector's own echo — a genuine publish from another client (e.g. the device itself reporting state) on the same topic still arrives normally.

**Subscribe QoS and Command (write) QoS are independent**, not one QoS reused for both. `PointConfig` gained `QoS` and `CommandQoS` fields (both zero-default-to-1, matching the pre-#119 hardcoded default); the Building-OS-sync path resolves them from gateway-side per-connector defaults (`MQTT_SYNC_DEFAULT_QOS_JSON` / `MQTT_SYNC_DEFAULT_COMMAND_QOS_JSON`, since the Point List has no QoS field of its own), and the static `MQTT_POINTS` env path gained matching optional `qos`/`command_qos` fields.

**A topic already covered by a static `MQTT_SUBSCRIPTIONS` wildcard filter never gets its own explicit Subscribe/Unsubscribe.** `MQTT_SUBSCRIPTIONS` (`+`/`#` filters) is fixed for the connector's lifetime and is not something Point-List sync manages. Without this check, a Point-List-synced topic already reachable through an existing wildcard would either (a) get a redundant explicit Subscribe — some brokers deliver a message once per *overlapping* subscription, so this can double-count telemetry — or (b) on removal, attempt an Unsubscribe against a filter it never itself subscribed to. `connector/mqtt/topicmatch.go` implements standard MQTT topic-filter matching (`+`, `#`, the `$`-prefix wildcard exclusion) so `newTopicIndex` can classify each point's topic as needing its own broker call or not; only the routing metadata (`topicIndex.points`) changes for a wildcard-covered topic. **Known limitation:** a writable synced point that happens to fall under a static wildcard cannot get per-topic `NoLocal` (the wildcard subscription itself has none) — Point-List-synced writable points should not be placed under a `MQTT_SUBSCRIPTIONS` wildcard filter.

**Revision is a content hash of the desired set**, not a Building OS ETag pass-through: `internal/mqttsync.revisionOf` sorts the derived `[]sdk.SubscriptionSpec` by topic and SHA-256s the JSON encoding (`"sha256:..."`, the same vocabulary Building OS's own Point List ETag uses). This satisfies "expose the applied revision" independent of whatever Building OS revision produced it, and changes exactly when the MQTT-relevant slice of the Point List changes — not on every unrelated Point List poll.

## Consequences

- New per-connector NATS subjects `cfg.mqtt.<connector_id>.status` / `.apply` (docs/connector-spec.md §2.4) are MQTT-only for now; extending live reload to BACnet/OPC-UA/WebSocket/ZeroMQ is out of scope and would need its own design (BACnet in particular has no equivalent of MQTT5 No Local for its COV subscriptions).
- Apply is **operator-gated**, not automatic on every Point List poll: `internal/mqttsync` only computes previews on demand; nothing is pushed to a connector until `POST /connectors/{id}/mqtt-subscriptions/apply` (RoleOperator). This is a deliberate asymmetry with the Normalizer resolver, which does reconverge automatically — an MQTT subscription change has broker-visible side effects (extra load, an operator may want to stage it), the Normalizer reload does not.
- `runFreshnessFloor` now reads `c.topics` fresh on every republish tick instead of a snapshot captured at `Run()` startup, so a point added by a live apply gets correct freshness-floor metadata immediately rather than after a restart.
- The Admin UI preview/apply screen (`admin-ui/app/connectors/[id]/mqtt-sync/`) follows the existing catalog page's GET-diff → operator-gated POST → toast pattern (ADR-0006's Install/Update flow), not a new UI idiom.
